What it is

Nexora combines four things that are normally four separate products: Kanban boards and tickets for the work itself; a documentation workspace with a nested page tree and a live editor; an AI assistant with real access to the workspace that reads through the asking person’s own permissions and can draft changes for a human to confirm; and integrations with the tools engineering already lives in — GitHub, Slack and SMS.

It is a single Laravel application, server-rendered, deployed as one Docker image run three ways. There is no separate front-end application, no API gateway and no microservices.

The problem it solves

Problem one
Customers cannot see progress without a person exporting it

Status meetings exist because nobody outside the team can read the board. Nexora gives the customer a real login to the real board — and answers the obvious objection by making internal the default for everything, with publication a deliberate, audited, staff-only act.

Problem two
Internal candour and customer communication collide

A team that shares its board stops writing frankly on it. Nexora gives every ticket two conversation streams — one the customer takes part in, one the customer cannot see, cannot count and cannot detect — so the team keeps its working notes without keeping a second system.

Problem three
Knowing what is happening costs time

Somebody has to read forty tickets to answer “what is overdue?”, or open GitHub to answer “did that ship?”. Nexora’s assistant answers those from the live workspace, using retrieval tools scoped to the asker, and will draft the ticket that should follow.

Who uses it

Delivery team membersteamDaily work: tickets, documentation, the assistant, integrations, and board configuration for boards they belong to

There is no self-service sign-up by default. ALLOW_PUBLIC_REGISTRATION is false and an administrator creates accounts. When enabled, a self-registered account receives the least-privileged role, customer — never staff.

A denial is 404, never 403, wherever existence is itself a secret — a 403 on /boards/acme-platform would confirm that such a board exists.

Where the rule is enforced

Four independent layers, designed to overlap. Authorization is applied in SQL first and in policies second: a collection is filtered by a query scope, and a single loaded record is then checked by the matching policy method. Each policy is written to mirror its scope line for line.

01
Route middleware
role:admin,team blocks before a component exists; password.confirm re-authenticates for administration screens. Coarse only.
02
Query scopes
The primary defence. Ticket::visibleTo(), Comment::visibleTo(), AiRun::visibleTo() and DocPageFinder filter in SQL — which protects lists, search, counts and links at once.
03
Policies
Eight of them. A single loaded record is checked against the scope it came from. Attachments hold no rules of their own — they resolve their owner and ask that record’s policy.
04
Actions
Field-level rules that hold whatever calls them — a screen, a console command, or a confirmed AI proposal. There is no second, weaker path into the same tables.
The design decision that carries the most weight customer_visible is stored positively and defaults to false on both tickets and documentation pages, so a row created by code that forgets to set it is internal rather than exposed. It is deliberately not mass-assignable: only the ticket actions can set it. The same applies to a comment’s stream — staff choose explicitly, and the default when nothing is said is internal, so a code path that forgets to choose keeps quiet rather than publishing to a client.
Why customers get a narrower kind of refusal A customer’s restricted fields are silently dropped rather than rejected. The ticket policy permits a customer to edit a ticket they raised; the action is what narrows which fields they may touch. So a crafted request that submits assignee_id, estimate or customer_visible cannot set any of them, even though the update itself is authorized.

04

Boards and tickets

A board is the unit of work, the unit of access and the unit of configuration. Access to Nexora is access to a set of boards; there is no entity above one.

The board

A board carries a globally unique slug used in every URL and a globally unique ticket prefix of two to six characters. Primary keys are never exposed. On creation it receives one tab, Main, with the standard workflow — Backlog, To Do, In Progress, Review, Done — with Done marked terminal.

Board options live in a JSON settings column read through a helper that falls back to configuration defaults, so a new board option needs no migration and no backfill. Columns are unique per tab and reorderable; deleting one moves its tickets out one at a time and deliberately suppresses the “moved to” notification, because otherwise tidying a board would notify everyone assigned a card on it.

Tabs

A board can be split into tabs — “Admin dashboard”, “Public website” — like browser tabs: one board, several boards’ worth of work. Each tab has its own columns; the strip above the columns switches between them without leaving the board, keeps the filters on, and shows each tab’s count of matching tickets. A ticket has no tab of its own: its tab is its column’s tab, enforced by a composite foreign key, so a ticket can never sit in another tab’s column.

The delivery team adds, renames, reorders and removes tabs from the strip itself. A new tab copies the open tab’s columns; deleting a tab never deletes its tickets — they move to the tab chosen, by column name, then done to done, then the first column, and the panel shows where each will go first. A ticket moves between tabs by dragging its card onto a tab, from the ticket page, or through the assistant and MCP, which take an optional tab. Customers see every tab’s name, as they see columns, but only their own tickets and counts.

Importing files as pages

Import file beside + New page, Import a file in an empty documentation section, and Import a file inside this one on any page — and the sidebar and the empty state take dropped files. PDF, Word, text, Markdown, CSV, Excel and PowerPoint files each become an internal page with the original attached, keeping the structure a to-do or bug list is made of: headings, nested lists, checkboxes as to-dos, tables, links. A scanned PDF or a legacy .doc is refused with what to do; one bad file never stops the rest. Office XML is read with a streaming reader that refuses any document type declaration, inside the existing zip-bomb limits, and large files are converted on the queue.

A page with open to-dos shows Create tickets with AI: the assistant opens on that page’s board, in Writing, with the request written — nothing is created until it is confirmed.

The ancestor visibility rule

A tree needs one rule a flat table does not A page is visible only when it and every one of its ancestors are visible. Publishing a child of an internal page would otherwise show a customer a page whose parent, path and siblings they must not see — and the breadcrumb alone would leak the internal titles.

It is enforced in three deliberately overlapping places: on write, publishing is refused when a parent is internal and “make internal” cascades down the whole subtree; on reading one page, the finder walks the ancestor chain through the visibility scope and 404s if any link is missing; and on reading the tree, any node whose parent is not in the visible set is dropped, so a broken invariant cannot surface as an orphan.

The two operations are deliberately asymmetric. Publishing is refused rather than silently publishing the ancestors too, because exposing a parent page is the author’s decision, not a side effect. Un-publishing cascades, because anything else would leave published children hanging off an internal parent. Retracting always fails closed: more is hidden, never less.

The editor is not a mode

Anybody who may edit a page gets the editor immediately, on the page they opened. There is no Edit button and no read-only step in front of it: a documentation tool whose default state is “looking at” rather than “working on” makes every small correction a four-click job, which is how documentation goes stale. A reader who may not edit gets the rendered document, and never so much as the markup of a control they could not use.

The editor is TipTap (ProseMirror), registered as an Alpine component and used headless, so the toolbar is ordinary Blade buttons styled like every other button in the product. Supported: headings, bold, italic, underline, strikethrough, inline code, code blocks with syntax highlighting, links, bullet, ordered and task lists, block quotes, horizontal rules, images and tables.

Markdown is the storage format The WYSIWYG editor is a surface over Markdown, and the HTML-to-Markdown conversion happens server-side. The stored artefact is always body_md, which keeps documents readable, searchable, diffable and exportable without the editor — and means a future change to how documents are rendered cannot alter what was stored.

The workspace AI

Nexora’s largest subsystem — roughly a third of the application’s classes. Almost every question about AI behaviour resolves to one of three settings, and none of them can grant what another refuses.

SettingWho chooses itWhat it decides
Capability modeAn administrator for the workspace; the team for a boardThe ceiling on what the AI may ever attempt here
Chat modeThe person asking, per conversationWhat this conversation is for — reading, writing, or both
Knowledge scopeThe person asking, per conversationWhere an answer may be sourced from

Capability mode — the security dial

ModeRead and answerPropose writesTicket analysisWrite codeRun unattended
AI ObserverYesNoNoNoNo
AI OperatorYesConfirmed by a personSuggest runsNoNo
AI AgentYesYesSuggest and applyYesYes

Three cumulative levels rather than a matrix of switches, because a matrix reads well on a settings screen and is impossible to reason about in a security review. Observer refuses ticket runs entirely, and that is stricter than people expect on purpose: a suggest run ends by posting an internal note, and a note is a write.

The capability mode is a ceiling, never a floor Every method on the capability guard can only ever deny. Raising a workspace to AI Agent gives no user a capability they did not already have by hand. The order of checks on any write is always: (1) may this person use the assistant at all, decided by the route group, board policy and SQL scopes; (2) does the mode permit the AI to attempt this; (3) is this person allowed to make this change, applied against the confirming user by the ordinary action.

Chat mode and knowledge scope

Chat mode
Reading · Writing · Everything

Reading is the default, so the setting somebody gets by not choosing is the one that changes nothing. Writing withholds the lookups so that “write me a ticket for the login bug” does not become four searches and a summary before it gets to the draft. Each mode names its own model, because lookup-and-summarise and drafting-something-actionable have different shapes.

Knowledge scope
Project only · Outside Project

Project only is the default and is not configurable away. Outside is additive, never a replacement — the board context still goes in and a question about NL-5 is still answered from NL-5, because “compare our architecture with a typical Laravel SaaS” needs both halves at once.

Knowledge scope has nothing to do with authorization Switching it does not widen what a person may read by a single row. It is enforced by the data layer — the tool registry decides which tools exist for a turn — not by the prompt. One honest limit is written down in the code: a language model’s own trained knowledge is not a data source this application can withhold, so under Project the assistant is instructed to decline general questions, and that is a prompt rather than a wall. What the data layer does guarantee is narrower and stronger: no external service is contacted, and no project data is widened either way.

Four promises made structural

Schema
Enforced before entry

Each tool declares its schema, and a call that does not fit is answered with prose the model can act on — not an exception.

Authorization
The asker is the viewer

A tool argument names a subject; the viewer comes from the request. An assistant with tools answers more questions than one without, about exactly the same material.

Containment
A tool that throws is contained

The exception is logged in full and reported to the model as “that lookup failed”, with nothing about why — a message can carry a query, a path or a column name.

Audit
One row per call, whatever the outcome

Written to ai_tool_invocations. A refused call is the interesting one to have a record of.

The loop is bounded at 4 rounds, 6 calls per round and 60,000 characters of tool material per question. Those are cost and latency controls, not security controls — turning tools off narrows what the assistant can answer and grants nobody anything.

Write tools: propose, then confirm

Seven action types, each exposed to the model as propose_<name>. The prefix is deliberate: the name itself tells the model that calling it does not perform the action. Six are reversible — create and update a ticket, comment on one, create and update a documentation page, start a code run. One is destructive — delete a ticket — and is always confirmed by typing the ticket’s key by hand, in every mode.

Step 1Model emits one proposal. One is kept per turn — a preview showing two unrelated changes invites confirming both while reading one — except new tickets: up to 30 of them are one proposal, previewed as a list and created all or none
Step 2Under Operator: a preview and a Confirm button. Under Agent: reversible actions are carried out immediately
Step 3The target is re-resolved from the stored proposal, through readers that apply visibility
Step 4The capability mode is re-checked — a preview can be on screen when an administrator lowers it
Step 5Gate checks run against the confirming user, per field, all before any write
Step 6The ordinary action is called — every rule it owns still applies
What the schemas deliberately cannot express Visibility can only be narrowed, and only at creation. A new ticket starts from the board’s default (customer-visible unless the board says otherwise) and the assistant may make it internal, never more visible than that. Publishing an existing ticket is not reachable from the chat. There is no field that can name a viewer, a user id, a column id or a label id. Assignees, columns and labels are named in words — “Alex Round”, “In Progress”, “bug” — because a name has to be resolved, and that is the step where the resolver can refuse an assignee who is not on the board and ask which of two matching columns was meant.

Authorization is per field, and happens first. A request to move a card and re-assign it asks both policies, and both are taken before either write happens — so a team member who may move but not assign changes nothing at all and is told why, rather than getting a moved card, a dropped assignee and a vague error.

A conversation belongs to one person — an administrator included There is no reading right over a colleague’s thread, and therefore none over the documents in it. Every denial is a 404. Transcripts persist; prompts do not — the system prompt and the context are rebuilt on every request, so editing a board’s project context changes the next answer instead of being frozen into an old row.

The whole conversation, cached. Each question replays the conversation in full, up to the model’s real context window — a million tokens for Opus 5 and Sonnet 5 — and asks the provider to cache it, so the repeat costs a tenth of a fresh send. A conversation that outgrows the window loses its oldest part in one jump, from a question, and the beginning then stays the same so the cache keeps working. Files stay with the question they came in on. The note above the composer now says when the conversation nearly fills what the model can read at once; the per-conversation spending cap is off by default.

Usage is recorded per exchange with a usage_reported flag: a run whose token counts were never reported has no cost and is shown as an unpriced run rather than folded in as zero. Pricing lives in exactly one place, and a model that is not listed produces a null cost rather than a guess.

Charts, voice and attachments

Visualisation
Seven chart types, drawn server-side

Line, bar, horizontal bar, area, pie, donut and scatter, plus tables and KPI rows. The model never supplies anything that is executed or rendered directly — it supplies numbers and labels, which are validated into typed specs, and the server draws the SVG from those. Colours come from a fixed palette chosen by index. Failure is always prose: a malformed chart falls back to the text the model wrote.

Export
CSV by block index, PNG in the browser

The CSV route re-reads the stored answer and re-parses it with the same parser the screen used, then exports block N — it addresses an index rather than accepting a payload, because a browser that could POST its rows could export rows the model never produced. PNG is produced from the SVG already on the page.

Voice
Three steps, not a fourth kind of session

Speech-to-text, the ordinary assistant, text-to-speech — which is what lets a spoken question inherit sessions, attachments, capability modes, the audit trail and the customer boundary without any of them being taught about voice. Generated audio is bytes, never a file, and there is deliberately no cache.

Attachments
Seven kinds, kept with their message

Text, Markdown, CSV, PDF, image, audio and Office documents. A file goes in whole with the question it came in on and is replayed with it on every later turn, from the cache, so a long to-do list can be finished with “continue”. Word files arrive with their headings, lists and checkboxes. Every truncation is stated in the prompt, because a model handed half a contract and not told will summarise it as though it read the end.

Import
A file into the docs, and its tickets

“Import this into the docs and make the tickets” is one proposal: propose_import_document makes an internal page whose body is the whole file, converted on the server — never retyped by the model — and a ticket for each open to-do and bug, internal unless asked otherwise, all or nothing. A page with open to-dos offers Create tickets with AI, which opens the assistant on that page.

CSV rows are sent as data and the profile — column types, ranges, outliers — is computed from all of them, so a question about an average is answered from every row even when only the first 300 are quoted. Images are re-encoded rather than forwarded, stripping EXIF including GPS, and are sent as pictures only to models that declare vision. An instruction inside an uploaded document is framed to the model as text somebody wrote, never a command.

From Claude or ChatGPT (remote MCP)

People add https://<host>/mcp to Claude or ChatGPT as a custom connector, sign in with their Nexora account, and then ask questions — or ask for changes — from there. Reading uses the same ten tools through the same registry, so an answer cannot differ from what the in-app assistant would read for the same person. Changes go through the same code a confirmed proposal does (ExecuteChatAction::perform()), as the person, within the board’s AI mode, and every call is audited on the mcp channel.

Three changes wait for a yes

Deleting a ticket, a comment the customer will read and editing a published page answer “confirmation needed” with a one-time code bound to the person, the target and the exact arguments. Everything else happens on the call — the AI app has already asked the person.

Safe
Retries, races, runaways

An identical request within 90 seconds returns the first answer instead of a duplicate; a ticket changed since it was read is not overwritten; changes are limited to 30 a minute per person; MCP_WRITES_ENABLED=false returns to read-only without a deploy.

Honest
The answer is the saved row

Every reply is read back from the database: what changed, old → new. A refusal says why; a ticket the person cannot see reads exactly like one that does not exist.

Traced
“via Claude” in the history

The person is always the actor; the ticket history and activity feed add the app it came through.

How it looks in the chat. The server tells the AI app to answer in the chat, never in an artifact: one ticket as a bold linked line with bullets, several as a table Ticket | Title | Status | Assigned to | Priority | Due, status and assignee always shown separately. The tools put status colours in their own output — 🟢 done, 🟡 in progress, 🟣 review, 🔴 blocked, ⚪ not started — worked out from the real column, with its name kept, plus 👤 for the assignee (Unassigned when nobody has it) and a link on every ticket key. Connections approved while the server was read-only were signed out once, so everybody agrees to the new screen.

AI ticket runs

A run is the AI working on one ticket, off the request cycle, on its own queue. It is a different feature from the assistant: the assistant is a conversation, a run is a job with a result.

ModeWhat it doesRequires
SuggestReads the ticket and repository metadata, writes an opinion as an internal note on the ticketAI Operator or above
ApplyWorks in an isolated clone, on a new branch, runs the configured tests, and opens a draft pull requestAI Agent, a GitHub token, an attached repository, and a code-generation driver

The apply pipeline

PreparingCheck the coding runtime exists; clone into the run’s own directory
RefuseIf the base branch is protected: main, master, production, release, develop
BranchCreate ai/NL-42-<uuid> off the base
CodingThe runtime edits files; the diff is re-derived from git status, not from what it claimed
RefuseAn empty diff fails the run — no pull request is opened for work that did not happen
TestingRun the configured validation commands
RefuseA non-zero exit fails the run, before anything is pushed
Pull requestCommit, push the new branch only, open a draft PR
FinishedInternal note with the branch and the PR link; usage recorded; directory deleted

Three invariants that are structural, not instructions

Invariant
Never pushes to main

The push is always to a generated branch ref. The base branch is only ever read, and a protected base is refused outright.

Invariant
Never merges

The pull-request client has no merge method, no branch-delete method and no review-approval method. The capability is absent from the codebase, so apply mode could not merge even if the token allowed it — and the token is never given merge rights.

Invariant
Never fakes success

An empty diff, a failed validation command or an unavailable runtime all raise. The run is recorded as failed and an internal note names the step that stopped it.

Caps, and the asymmetry between them

TriggerWho starts itCapBypass
ManualA staff member presses a button on the ticket100/dayAdministrators may exceed it, if configured
AutomaticA customer’s ticket is created, if the board opts in20/day per boardNobody. Ever.

Nobody chose the automatic runs — a customer filing twenty tickets in an afternoon starts twenty runs, and on apply mode that is twenty clones and twenty pull requests. There is no bypass for the automatic cap because there is nobody to grant one to. “Today” is the board’s own day, so a board configured for Europe/Stockholm rolls over at Stockholm midnight. Cancelled runs do not count, since they never started.

Apply mode is partially implemented as shipped AI_CODE_DRIVER defaults to unavailable, and with that setting an apply run fails immediately with an internal note naming exactly what is missing. Nothing is faked and no empty pull request is opened. The working driver is claude_code, which runs the Claude Code CLI inside the isolated checkout and needs the binary (already installed in the Docker image) plus an API key in the worker’s environment. Repository cloning is separately opt-in and defaults to off; with it off, suggest mode still runs and records that the working tree was unavailable rather than pretending it read the code.

Durability

Duplicate execution is guarded twice, because the two guards fail differently: a cache lock stops two workers starting the same run at the same moment, and an authoritative status claim flips queued to running in a single conditional update and checks the affected row count. Only transient provider failures are retried — a missing credential, an unavailable runtime, a protected branch or a failed test suite would fail identically three times, so those stop on the first attempt rather than producing three identical internal notes twenty minutes apart.

A run is owned by the job that claimed it, so if that job disappears — a deploy, a restart, an out-of-memory kill — the ticket would show “Running” for ever. A scheduled command recovers stranded runs every ten minutes, and refuses to touch a run that still has a job on the queue.

A customer has no relationship with AI runs at all Not “cannot start one” — cannot see that they exist, cannot see a status, a cost or a failure. Every ability denies a customer as 404, because a 403 on “AI runs for AQD-42” would confirm the feature is being used on their ticket.

Integrations

Three outward connections, each off until credentials exist, and each failing loudly rather than pretending.

GitHub

DirectionWhat it does
InboundGitHub tells Nexora about branches, commits, pull requests and CI that mention a ticket key
OutboundApply mode pushes a branch and opens a draft pull request

A developer writes NL-42 in a branch name or a commit message. GitHub posts a signed delivery; Nexora rate-limits it, verifies an HMAC-SHA256 digest over the raw body in constant time, records the delivery id under a unique index — the insert is the de-duplication claim — queues the work and answers 202 in well under GitHub’s ten-second budget. A worker then resolves the reference and upserts a link on the ticket timeline.

The security boundary is the repository, not the pattern A webhook is an anonymous request whose only credential proves GitHub sent it — it does not prove who owns the repository it is about. So a delivery may only reach tickets on boards where an administrator has already attached that repository. The repository name in the payload is matched against the attachment table, and the resulting board ids are the only boards in scope. A repository nobody has configured resolves to nothing and the delivery is recorded as ignored.

Slack

Configured per board rather than per workspace, because that is how the product is used: each customer’s board belongs to a different delivery team with a different channel. The webhook URL therefore lives on the board, encrypted at rest — a Slack incoming-webhook URL is a bearer token wearing a URL’s clothes, and Slack has no read-only variant.

EventDefaultFires when
customer_ticket_raisedOnSomebody outside the delivery team files a new ticket

Why a Slack message is deliberately thin A Slack channel is outside this application’s authorization model. Whoever is in the room reads the message, and Nexora has no idea which of them is a board member, which is a customer and which is a contractor added last week. So a message carries an identifier, a title, who did it, and a link — never a description, a comment body or an AI summary. The link is the access control: following it requires logging in, and the ordinary visibility rules then apply.

SMS

An SMS is the most intrusive notification this application can send: it reaches a person who is not at a computer, possibly asleep, and it costs money per message. So it has exactly one trigger — a critical ticket being raised — and it is off until somebody deliberately turns it on.

Recipients are numbers rather than users, on purpose: on-call is a rota, not a role, and the person carrying the phone this week is often not the person whose account raised the board. A hard ceiling of five recipients applies whatever a board is configured with. Duplicates are suppressed by a unique index per ticket per number, plus a per-board cooldown — so if a script files forty critical tickets in a minute, the on-call phone rings once.

Each record holds a phone number, which is personal data, so the table has a retention window of 90 days rather than growing for ever — long enough to answer “was the on-call rota reached about that incident?” without keeping it indefinitely. On the integrations screen the rota field is readable, because somebody has to be able to remove a colleague’s number when they leave it; the delivery history below it is masked.

Reporting and realtime

Two statistics screens, not one screen with a role switch

The separation is the safety property A shared class with a “for customer” flag would mean every future metric somebody adds is exposed by default and has to be remembered not to be — the wrong way round. Here the customer screen can only render what its own service offers, and that class offers six things. There is no branch on either page that a careless edit could invert.
ScreenWhoMetrics
Team statisticsStaff onlyCounts, by column, by priority, by assignee, by label, created by week, visibility split; flow metrics; AI usage and cost
Customer summaryEveryone, staff includedCounts, by priority, open versus closed, created by week, recent activity, recent tickets

The customer screen is open to staff deliberately: it is the only way for a team member to see exactly what a customer sees. When they open it they see their own visibility, not a simulated customer’s, and the screen says so.

Flow metrics come from history, never from current state

“Twelve tickets are in Done” is not throughput: those twelve might have arrived over two years, and the eight finished last month and then reopened are invisible. Flow is a property of transitions, so these are read from the append-only event table — which carries the board and both column ids as dedicated indexed columns precisely so that “which tickets entered a done column on this board last week” is one index range scan.

Two limitations are surfaced to the reader rather than hidden: a ticket that has never left its column contributes no interval to the time-in-column figures, because counting “so far” would make a healthy board look worse the longer it stays healthy; and the fold is bounded, so a range wide enough to exceed it reports that it was truncated instead of quietly averaging a subset.

Export

Dataset names are an allow-list — anything not in the list is refused rather than reflected, with no dynamic method call. Every dataset is derived from a scope resolved for the requesting viewer, so a CSV cannot contain a figure its requester could not see on screen. The date range is corrected rather than trusted: an unknown preset falls back to the default, reversed dates are swapped, and an absurd span is clamped to three years, so a hand-edited URL cannot ask the database for ten years of transitions. There is deliberately no per-ticket export — these are aggregates.

Realtime

ChannelWho may joinCarries
board.{id}.internalStaff members of that boardContent-free signals about internal changes
board.{id}.customerAnyone who may view the board, customers includedContent-free signals about customer-visible changes
users.{id}That user, while activeA nudge for the notification bell
Every channel is private — there is no public or presence channel Because the internal channel is only signalled for internal changes, a customer’s browser is never even woken by activity they are not allowed to know about — which closes the timing side-channel a single shared channel would leave open even with an empty payload. The rule for tickets is subtler than “is it customer-visible?”: a ticket that has just been hidden also changes what customers see, so the customer audience is signalled when the ticket is customer-visible now or was before the change.

Events are dispatched after the surrounding transaction commits — broadcasting a change that then rolls back would tell every open board to re-read something that never happened. Realtime is optional: with broadcasting switched off everything still works, screens simply do not refresh by themselves.

Search, notifications and activity

Cmd / Ctrl + K
Command palette

Four categories — tickets, documentation, boards, people — at most five hits each, each filtered by the same visibility scopes the screens use. Pasting a ticket key resolves it as an indexed key seek and puts it at the top.

Bell
Notifications

Holds no data of its own. Everything is re-read on each render and re-checked against the visibility scopes, so what is shown is what the viewer may see now, not what they were allowed to see when it was written.

Workspace activity feed

Ticket movement, assignments, comments, documentation changes and board configuration, newest first. Staff only, enforced three times — route middleware, a component check, and a SQL refusal — because every description is written for the delivery team.

Appearance
Light, dark, system

Three states rather than a boolean, because “follow the operating system” is a genuine third answer. The preference is stored on the user row so it follows a person between devices, cached in local storage, and applied by an inline script before the bundle downloads so there is no flash of the wrong theme.

Search is plain SQL, on purpose There is no Scout, Meilisearch, Algolia or Elasticsearch. An external index has no idea that a ticket is internal, so the filtering would have to be reproduced in the engine’s query language, correctly, for ever — and it would hold a second copy of every ticket description outside this application’s visibility rules. The documented next step, when LIKE stops scaling, is a MySQL FULLTEXT index, which stays inside MySQL and needs no new service. Scout is the step after that.

Credential screens render presence and the last four characters, never the value; the vault has no method that would return a key to a component. Somebody who gains access to those screens can replace a credential — which is visible in the rotation timestamp and the updating user — but cannot read one out. Decryption failure degrades to “not configured” rather than throwing, so rotating the application key makes a board stop posting to Slack instead of breaking every ticket save.

The GitHub token is deliberately weak: it needs exactly contents: write to push a branch and pull_requests: write to open one. It is never given merge rights, and the client has no merge method, so a future phase that genuinely needs to merge has to add the capability and be reviewed for it.

Input and output

Rendering
One pipeline for all user prose

Markdown to HTML with raw HTML stripped and unsafe link schemes rejected, then mentions highlighted and ticket references linked — but only for tickets the particular reader may open. Because steps two and three are viewer-dependent, nothing in this pipeline may be cached across viewers.

Editor
An allow-list in both directions

Browser to server, the posted document is attacker-controlled, so it is cleaned before the Markdown converter sees it — nothing hostile is stored, not even as inert text that would still surface in search results, board cards and AI prompts. An allow-list, because a deny-list has to anticipate whatever parser-confusion trick lands in browsers next year.

Model output
Never rendered directly

Charts, tables and KPI rows are validated into typed value objects before anything is drawn. There is no charting library receiving model-authored configuration, so there is no option in such a library that turns a string into a callback.

Uploads
Two ceilings, two allow-lists

Record attachments cap at 10 MB and 20 per owner; AI conversation files at 20 MB and 10 per conversation, and must pass both an extension allow-list and the detected MIME type. Stored paths are generated, never derived from the uploaded filename.

Two absences in the AI allow-list are deliberate: SVG, because it is a document that can carry script rather than a picture, and here an “image” is decoded and sent to a vision model; and ZIP, a container whose contents nothing has validated. Downloads never link straight at stored bytes — every request is authorized against the owning record first, then redirected to a signed URL valid for five minutes.

Webhook signature verification

PropertyImplementation
Fail closed with no secretWith the secret unset, every delivery is rejected. There is no “skip verification when unconfigured” path

Deployment and operations

One Docker image, built in three stages, run as three Railway services with three different start commands — so the worker image cannot drift from the web image.

Service
web

Supervisor running PHP-FPM, nginx, and a queue worker dedicated to the attachments queue. Health-checked at /health.

Service
worker

queue:work --queue=ai,default, three tries, restarted always. The ai queue is named explicitly and listed first — a bare queue:work listens only to default and would leave every AI run queued for ever.

Service
reverb

The WebSocket server, on its own public domain. One replica only — Reverb holds its connections in the memory of the process that accepted them, so a second replica would only reach half the clients.

The three queues

QueueCarriesRuns in
aiTicket runsworker — a run takes minutes, and must never delay a broadcast
defaultBroadcasts, in-app notifications, GitHub webhook processing, Slack, SMSworker — millisecond work
attachmentsAI file processingThe web container — see below
Why attachment processing runs in the web container The reason is the disk rather than the workload. The job opens the file that was just uploaded, and on a deployment whose attachment disk is a Railway volume, a volume attaches to exactly one service — so the upload request writes the file in the web container and a worker in the other container asks its own mount and finds nothing. Worse, a missing object is a legitimate condition in the reader, so the row settles into failed with no exception and nothing in the log to chase. An S3-backed deployment has no such constraint and can consolidate the queues.
The single most common misconfiguration Without a queue worker, several features silently do nothing — and nothing errors, because all of it is queued by design. Realtime updates never arrive, no Slack message is posted, no SMS is sent, no pull request is ever linked to a ticket, and every AI run stays queued for ever.

Scheduled housekeeping

ScheduleCommandPurpose
Every 10 minutesai:reap-stalledRecover runs stranded by a worker that died mid-run

Everything scheduled is housekeeping. Nothing a user waits for is scheduled, and nothing here is required for the application to function — a deployment with no scheduler works, it simply accumulates rows. The exception worth watching is the stalled-run reaper. Failed jobs are not retried automatically, because blindly replaying a batch would re-post internal notes and re-send messages.

Build-time versus run-time configuration

The realtime client keys are build arguments, not runtime variables Vite inlines them at build time, and the client only constructs its connection when a key is present. An image built without one ships a browser bundle that never subscribes to anything, whatever the server is configured to broadcast — so changing one requires a rebuild of the web image, not a restart. Only the public key belongs in that stage; the app secret must never be passed there, because everything in it is readable in the shipped JavaScript.

The application is configured by 180 environment variables. The entrypoint aborts if the application key is unset, caches configuration, routes, views and events at boot, and optionally runs migrations with an isolation lock.

Findings and next steps

Twelve items found while compiling this document. None is a functional defect in itself, but each is worth an owner. They are ordered by how cheaply they can be closed against how much risk they carry.

#FindingSuggested action
01Product naming is inconsistent. The runtime workspace name defaults to Aqueduct Workspace and the package is aqueduct/workspace, but the AI system prompt, source comments and one accessibility label say Nexora. A deployment that has not set the name presents as Aqueduct while its assistant calls itself NexoraDecide the product name and set WORKSPACE_NAME and WORKSPACE_SHORT_NAME accordingly
02No version identifier anywhere. No git tag, no version field, no application constantAdopt tags, and surface a version in /health. Support and rollback currently have no vocabulary
03No CI configuration in the repository. A 139-file suite with a dedicated fast security gate exists, but nothing runs it automaticallyRun the security suite on every push and the full suite on merge. This is the single highest-value item on the list
04A date-sensitive assertion in the security suite fails on roughly a third of calendar days, for no real reason — and it fails in the suite people trust mostNarrow the assertion to (total 7) rather than the bare digit
05Two pre-existing theme test failures. Not a regression, but two permanently red testsFix or quarantine, so that “green” means green
06README.md is empty. Two source files refer readers to “the deployment notes in README.md”, which do not existPopulate it, or point it at this document
07The demo seeder contains passwords in source, documented as a deliberate demo trade-offChange those accounts before anything real lands, as the class itself instructs
08No Content-Security-Policy or HSTS header. Two cheap defence-in-depth controlsAdd both at nginx. HSTS in particular is near-free on a platform that already terminates TLS
09SESSION_SECURE_COOKIE ships as false. Correct for local HTTP, wrong for productionAdd it to a deployment checklist
10The default capability mode disagrees with itself — configuration says agent, the database column default says observer. Both are deliberate and documented, but a deployment’s effective posture depends on whether a settings row existsDecide one, or explain the interaction on the admin screen. A fresh deployment wanting the cautious posture should set the mode explicitly
11Ticket type has no behaviour. Stored and filterable, but nothing differs between a bug and a featureEither give it behaviour or document it as a label
12Board archiving has no interface. The column and scope exist and nothing can reach themAdd the control, or remove the column
What none of these are None of the twelve is a breach of the customer boundary, a data-loss risk or a functional regression. The boundary is enforced in four overlapping layers and asserted by 28 dedicated security test files; the two most consequential items on this list are operational — no CI pipeline and no version identifier — and both are a day’s work.

Glossary

The terms this product uses, in the sense it uses them.

Board
The unit of work, access and configuration. Everything hangs off one, and there is no entity above it.
Board member
An explicit row linking a person to a board. This is the access grant; administrators bypass it.
Ticket key
The human identifier — the board’s prefix, a hyphen, the per-board number, as in NL-42. What GitHub branches and commits reference.
Customer
The security boundary of the product. May never observe internal content, on any board, including boards they belong to.
Staff
Administrators and team members together — the set that may see internal content.
Customer-visible
The positive visibility flag on a ticket or page. Defaults to false, so anything created by code that forgets to set it is internal.
Internal note
A comment in the internal stream. Customers cannot read it, count it, or detect that it exists.
Stream
Which conversation a comment belongs to: customer or internal.
Capability mode
The administrator’s ceiling on what the AI may ever attempt: Observer, Operator or Agent.
AI Observer
The most restrictive mode. Reads and answers; writes nothing, not even an internal note — so no ticket run may start.
AI Operator
The middle mode. Proposes changes a person confirms, and permits manual suggest runs.
AI Agent
The most permissive mode. Adds unattended work: automatic runs, apply-mode pull requests, and reversible changes carried out without a confirmation step.
Chat mode
The asker’s choice per conversation: Reading, Writing or Everything.
Knowledge scope
Where an answer may be sourced from: Project only (the default) or Outside Project, which adds general knowledge alongside the project and widens data access by nothing.
Proposal
A change the AI has described. A preview until a person confirms it — at which point it is re-resolved, re-authorized and executed through the ordinary action.
Run
One AI working session on one ticket. Suggest (posts an internal note) or apply (opens a draft pull request).
Tool
A read-only lookup the AI may call. Runs with the asking person as the viewer, and is audited whatever the outcome.
Draft (documentation)
The autosave buffer for a published page. Nothing renders it to a reader.
Slug
The URL identifier for a board or page. Primary keys are never exposed.
Workspace
The whole deployment. Not an entity — there is no workspace table.
